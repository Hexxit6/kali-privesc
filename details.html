Security research report · 28 October 2026

LightDM 1.33.1-4: local root through an untrusted X server

A local user on stock Kali can combine the public nested-seat D-Bus API, a malicious XSETTINGS manager, a Debian-specific shared-data symlink, and a PATH lookup to execute code as root. No password, user session, or custom host configuration is required.

SeverityCRITICAL   local privilege escalation to root
AffectedKali rolling 2026.3: lightdm 1.33.1-4, lightdm-gtk-greeter 2.0.9-1, GTK 3.24.52-2. Debian sid exact package: 1.33.1-4.

1. What the operator needs to know

1.1 Three privilege levels, not one

LightDM is not a single process. The daemon runs as root and owns the system bus name. A seat is a display position; the default local seat is Seat0, and an xremote seat is a display LightDM does not start itself. The greeter is the login UI, and it runs as the unprivileged lightdm account. When a user logs in, LightDM forks a session child; that child starts as root so it can set up the session, then drops to the authenticated user. The exploit crosses from the greeter account back into the root daemon, then into the root phase of a session child.

1.2 D-Bus is the front door

D-Bus is the system-wide message bus. A process sends a method call to a bus name; the bus applies an XML policy and then delivers it to the owning process. For LightDM, the daemon owns org.freedesktop.DisplayManager. The default policy allows any local sender to call the DisplayManager, Seat, and Session interfaces; only AddSeat is denied. The daemon does not inspect the caller's UID or the D-Bus sender field in the AddLocalXSeat handler.

1.3 The greeter is a privileged client of an untrusted display

The greeter is a GTK application. The X server is a separate process, and XSETTINGS is a property on that server: a settings manager publishes values such as theme names and module lists, and clients read them. GTK3's Gtk/Modules setting is a list of shared objects loaded with dlopen. LightDM normally connects the greeter to the local trusted display. AddLocalXSeat breaks that assumption by allowing the caller to choose the display number. The user owns the display, so the user owns the settings the greeter reads.

1.4 The greeter channel is a second, narrower front door

LightDM gives the greeter a Unix socket file descriptor. The greeter sends binary messages to the daemon, including START_SESSION, SET_LANGUAGE, and ENSURE_SHARED_DIR. The root daemon handles these messages in greeter.c. ENSURE_SHARED_DIR takes a username and calls shared_data_manager_ensure_user_dir(); that function runs as root and applies UID, GID, and mode to a path under USERS_DIR. The handler does not authenticate the greeter or validate that the path is still inside the data tree.

1.5 Debian's path move creates the pivot

Upstream LightDM uses USERS_DIR=/var/lib/lightdm-data, which is normally root-owned, so a greeter cannot replace its parent. Debian patch 06 changes it to /var/lib/lightdm/data. The parent /var/lib/lightdm is owned by lightdm, so the greeter can rename data and create a symlink in its place. The sink in shared-data-manager.c builds USERS_DIR/username and calls g_file_make_directory_with_parents() followed by g_file_set_attributes_from_info(). GLib resolves the symlink components when applying attributes; there is no openat, O_NOFOLLOW, or fchownat(AT_SYMLINK_NOFOLLOW).

2. The chain, stage by stage

The chain is easiest to read as three trust crossings. The user starts outside LightDM and asks the root daemon for a seat. The root daemon puts the greeter on the user's display, which turns the user's XSETTINGS into code in the greeter. The greeter then asks the root daemon to adjust a path that has been replaced with a symlink. The result is a directory the greeter can write; the next session start executes the planted binary as root.

Stage 1 · ask the root daemon for a seat

AddLocalXSeat is a public, unauthenticated D-Bus method

The system bus policy allows the DisplayManager interface to every local user. The only denied member is the deprecated AddSeat; AddLocalXSeat is intentionally callable without root. The daemon's method handler does not check the caller's UID or the D-Bus sender field. It creates an xremote seat and sets the caller-supplied display number.

For the xremote seat, the root daemon does not spawn an X server. It calls xcb_connect_to_display_with_auth_info on the address (the lab uses :99). The attacker starts Xvfb :99 -ac, so the root daemon and then the greeter connect to an attacker-owned display. The greeter is launched as the lightdm service account, not root.

Stage 2 · turn XSETTINGS into greeter code

Gtk/Modules is a GTK-wide module list

XSETTINGS is a property on the X server. A settings manager publishes a list of settings; GTK clients read them. The Gtk/Modules setting is a list of shared objects that GTK loads with dlopen. The implementation is a known GTK3 primitive (the same class as CVE-2026-76023, a Chromium GTK3 X11 sandbox escape). The new part here is the caller: the greeter is a privileged LightDM component attached to a display the attacker chose.

lab/xsettings_pwn.c — the attacker's XSETTINGS manager
/* Own _XSETTINGS_S0, then publish one string setting. */
XChangeProperty (d, win, _XSETTINGS_SETTINGS, ...);
XSetSelectionOwner (d, _XSETTINGS_S0, win, CurrentTime);

/* The value the greeter reads: */
Gtk/Modules "/var/tmp/libpwn.so"

The module's constructor runs inside the greeter process as lightdm. It has the greeter's environment and the greeter-to-server file descriptor in LIGHTDM_TO_SERVER_FD. The constructor can therefore do two things the greeter could do: manipulate files the lightdm user can manipulate, and send greeter protocol messages to the root daemon.

Stage 3 · replace the data directory with a symlink

The root daemon applies attributes through the symlink

The Debian patch changes the compile-time path from /var/lib/lightdm-data to /var/lib/lightdm/data. The parent /var/lib/lightdm is owned by lightdm, so the greeter can rename the existing data directory and replace it with a symlink to /usr/local. The greeter then sends ENSURE_SHARED_DIR("bin") over its existing file descriptor.

g_file_set_attributes_from_info() with G_FILE_QUERY_INFO_NONE follows the intermediate symlink. Because getpwnam("bin") succeeds, the target attributes are UID 2 (bin), GID of the greeter (lightdm), and mode 0770. The directory /usr/local/bin is now group-writable by lightdm. The exploit does not need to create a new directory; the existing directory is precisely what makes the EXISTS branch accept the path.

Stage 4 · make the next session child execute the fake

execlp searches the daemon's PATH

Every session start, including the greeter session, goes through session_real_start(). The root process forks and calls execlp("lightdm", ...) to re-enter its own binary in session-child mode. execlp searches the daemon's PATH. On Kali that path starts with /usr/local/bin, before /usr/sbin.

src/session.c:625
priv->pid = fork ();
if (priv->pid == 0)
{
    /* Run us again in session child mode */
    execlp ("lightdm",
            "lightdm",
            "--session-child",
            arg0, arg1, NULL);
    _exit (EXIT_FAILURE);
}

After stage 3, the greeter writes a fake /usr/local/bin/lightdm. The exploit triggers a second AddLocalXSeat(99); the daemon creates another greeter session, and session_real_start resolves the fake first. The fake runs as root, before the session child drops to lightdm. The lab fake writes a sudoers entry, copies /bin/sh to /var/tmp/rootsh, and makes that copy setuid. The order matters: chown clears the SUID bit, so the script chowns first and chmods 4755 second.

fake /usr/local/bin/lightdm
#!/bin/sh
id > /tmp/root_evidence.txt
echo 'attacker ALL=(ALL:ALL) NOPASSWD: ALL' > /etc/sudoers.d/pwn
chmod 0440 /etc/sudoers.d/pwn
cp /bin/sh /var/tmp/rootsh
chown root:root /var/tmp/rootsh
chmod 4755 /var/tmp/rootsh
